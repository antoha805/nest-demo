# nest-demo

Demo REST API built with NestJS, MikroORM and PostgreSQL.

Requires Node.js 22.17+ and Docker.

## Getting started

```bash
cp .env.example .env
docker compose up --watch
```

In a second terminal, add the sample data:

```bash
docker compose exec api npm run seed
```

The API is served at `http://localhost:3000/api` and reloads when files in `src` change. Postgres is exposed on host port `5433`, and Redis on `6380`.

To run the API on the host instead, start only the database and Redis:

```bash
npm install
docker compose up -d --wait postgres redis
npm run migration:run
npm run permissions:sync
npm run seed
npm run start:dev
```

## Migrations

The schema is managed by MikroORM migrations in `src/database/migrations`, run by `src/database/migrate.ts`. The app never changes the schema itself. `docker compose up` applies pending migrations when the `api` container starts.

Primary keys are UUID v7 values generated by the database's `uuidv7()` function, which requires Postgres 18 or newer.

After changing an entity, generate a migration from the host, with Postgres running and all existing migrations applied:

```bash
npm run migration:create -- AddPostSlug
```

This writes the difference between the entities and the database to a new file in `src/database/migrations`. Review it, then add its class to the end of the list in `src/database/migrations/index.ts`: migrations are listed there rather than found on disk, so they load the same way from `src` and `dist`.

Then apply it with `docker compose exec api npm run migration:run`, or `npm run migration:run` on the host. `npm run migration:revert` undoes the latest one, and `npm run migration:check` fails if the entities and the database differ.

The project moved from TypeORM, whose migrations kept their names. On a database TypeORM migrated, the first `migration:run` records them as applied from its `migrations` table instead of running them again. A later migration then drops that table. To deploy the TypeORM version again, first run `npm run migration:revert` once, which restores the table.

## Production image

```bash
docker build --target prod -t nest-demo .
```

The image contains no `.env`, so pass the settings below as environment variables when running it.

The app does not apply migrations on startup. Run them once as a deploy step before starting the new version:

```bash
docker run --rm --env-file prod.env nest-demo npm run migration:run:prod
docker run --rm --env-file prod.env nest-demo npm run permissions:sync:prod
```

## Production deployment

`docker-compose.prod.yml` runs the production image with Postgres, and applies pending migrations and syncs permissions before the API starts. Create `prod.env` from `.env.example` with a strong `DB_PASSWORD`; it is not committed. The file sets `DB_HOST`, `DB_PORT` and `LOG_TRANSPORTS` itself.

Build and push the image from another machine, as small instances can run out of memory while building. Match the instance's CPU architecture, for example `--platform linux/amd64` for `t3`:

```bash
API_IMAGE=registry.example.com/nest-demo docker compose -f docker-compose.prod.yml --env-file prod.env build
docker push registry.example.com/nest-demo
```

Then, on the instance, with `docker-compose.prod.yml` and `prod.env` in the same directory:

```bash
export API_IMAGE=registry.example.com/nest-demo
docker compose -f docker-compose.prod.yml --env-file prod.env pull api migrate
docker compose -f docker-compose.prod.yml --env-file prod.env up -d --no-build
```

Only Caddy is published to the host. It serves the API over HTTPS on port `443` and redirects port `80` to it, using a free Let's Encrypt certificate that it renews itself. Set `DOMAIN` in `prod.env` to a name that points to the instance, and allow both ports in the security group. `PORT` only sets the port inside the container.

### Automatic deployment

Each push to `main` runs the checks in `.github/workflows/deploy.yml`, then publishes an Arm image to `ghcr.io/antoha805/nest-demo`. A systemd timer on the instance checks for a new image and compose file every minute, and applies them with pending migrations.

To set up an instance, copy the `deploy` directory to it, add `API_IMAGE=ghcr.io/antoha805/nest-demo` to `prod.env`, then run:

```bash
sudo install -m 755 deploy/auto-deploy.sh /usr/local/bin/nest-demo-auto-deploy
sudo cp deploy/nest-demo-deploy.service deploy/nest-demo-deploy.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now nest-demo-deploy.timer
```

A failed deploy does not show up in GitHub. To see what the instance did, run `journalctl -u nest-demo-deploy -n 50`.

## Authentication and authorization

`POST /api/auth/register` and `POST /api/auth/login` return an `accessToken`. Send it as `Authorization: Bearer <token>`. Both endpoints allow 10 requests per minute per IP. These tokens work on every route except `/api/mcp`, which takes only the tokens MCP clients get through OAuth: see [Signing in with OAuth](#signing-in-with-oauth).

### Email confirmation

Registering mails a 6-digit code to the new user, who confirms their email by sending it to `POST /api/auth/verify-email` as `{ "code": "123456" }`. Until then, `GET /api/auth/me` shows `emailVerifiedAt: null` and no permissions: the user can log in, read, change their nickname and confirm, but not post, comment or like. Their roles apply as soon as they confirm.

- A code expires after 15 minutes, and stops working after 5 wrong tries, so it cannot be guessed. `verify-email` also allows 10 requests per minute per IP.
- `POST /api/auth/verify-email/resend` mails a new code, which replaces the old one, at most once a minute: sooner gets `429 Too Many Requests`. Once confirmed, it gets `409 Conflict`, and confirming again does nothing.
- Codes are stored as an HMAC keyed with `JWT_SECRET`, never as is, and only work for the account they were sent to.
- Users who registered before confirmation existed were marked as confirmed by the migration that added it.

A user holds roles, each role grants permissions, and permissions can also be granted to a user directly. They are read from the database on every request, so changes apply immediately to tokens already issued. Passwords are hashed with bcrypt.

New users get the `member` role. The API cannot grant the first admin, so register a user and promote them from the command line:

```bash
npm run make-admin -- alice@example.com
```

In production, use `docker compose -f docker-compose.prod.yml --env-file prod.env exec api npm run make-admin:prod -- alice@example.com`.

`npm run permissions:sync` makes the database match the permissions in the code, as the API can only assign them, not create them. It runs after migrations on every `docker compose up` and deploy, and is safe to re-run. `admin` always gets every permission and cannot be changed or deleted. `editor` and `member` are created with the permissions in `src/roles/permission-names.ts` if they are missing, so a deleted `editor` role comes back. After that they only get permissions that are new, so edits made through the API are kept. `member` cannot be renamed or deleted, as registration assigns it.

Every route requires a token unless marked `@Public()`. Permissions are checked with [CASL](https://casl.js.org): `src/casl/casl-ability.factory.ts` turns each permission a user holds into rules. To protect a route, add `@CheckPolicies((ability) => ability.can('create', Post))`, which responds with `403 Forbidden` if the check fails. Rules that depend on the record, like `posts.update.own`, need a guard that loads it, as `@PostAccess('update')` does in `src/posts/post-access.guard.ts`.

To add a permission, add it to `src/roles/permission-names.ts` and its rules to `PERMISSION_RULES` in the ability factory, which fails to compile until you do. The next sync inserts it and grants it to `admin` and to the roles that have it in their defaults.

Removing a name from that file makes the next sync delete the permission and all its grants, including those on custom roles and users, and deploying an older version does the same. Renaming counts as removing one and adding another, so custom roles and users lose it. To keep their grants, rename the permission in a migration, which runs before the sync.

A category that still has posts cannot be deleted (`409 Conflict`). Categories return `postsCount`, which only counts published posts, so it is the same for every user and does not reveal drafts.

Posts return their category whole, as `category`, and are given it as `categoryId` when created or edited.

A post's `authorId` is set to the logged-in user when it is created and cannot be changed through the API. It is `null` for older posts and sample data, and becomes `null` if the author is deleted.

The `.all` permissions apply to every post, and the `.own` ones only to posts the user wrote. Posts with no author need `.all`.

Posts are drafts until published, and publishing is final: a published post cannot become a draft again, even when it is edited. A post is published by sending `"published": true` when creating it or editing a draft, or with `PUT /api/posts/:id/publish`. All three need `posts.publish`, otherwise `403 Forbidden`, but the last one does not need the right to edit the post, so reviewers can publish posts they cannot change. It is idempotent and responds with `204 No Content`. Editing accepts only `true` for `published` (`false` is a `400 Bad Request`). Posts return `publishedAt`, when they were published, or `null` for drafts. Published posts are public. Drafts are visible only to their author and to users with `posts.publish`, and return `404 Not Found` to anyone else, so send the token on `GET` requests to see them.

Comments and likes follow the post: every route above returns `404 Not Found` if the user cannot read the post. Comments return their author as `author`, with only the `id` and `nickname`. They stay when their author is deleted, with `author` set to `null`, and are deleted with their post. Posts return their total as `commentsCount`, and `myLastCommentAt` holds when the logged-in user last commented on them, or `null` if they have not or no token was sent. Comments can only be edited by their author; `comments.delete.all` is for moderation.

Liking and unliking are idempotent and respond with `204 No Content`. Posts and comments return their total as `likesCount`, and `myLikeAt` holds when the logged-in user liked them, or `null` if they have not or no token was sent. The `likes` table is polymorphic: `likeableType` and `likeableId` point to a post or comment. As Postgres cannot enforce a foreign key on that, database triggers delete the likes along with their post or comment. Adding a new likeable type needs a new enum value and such a trigger.

## MCP

`/api/mcp` is a [Model Context Protocol](https://modelcontextprotocol.io) server, so AI clients such as Claude Code can use the blog. It is built on the official SDK, `@modelcontextprotocol/sdk`, in `src/mcp`. Its tools match the REST routes:

| Area          | Tools                                                                                                               |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| Posts         | `search_posts`, `get_post`, `create_post`, `update_post`, `delete_post`, `publish_post`, `like_post`, `unlike_post` |
| Comments      | `list_comments`, `create_comment`, `update_comment`, `delete_comment`, `like_comment`, `unlike_comment`             |
| Categories    | `list_categories`, `get_category`, `create_category`, `update_category`, `delete_category`                          |
| Notifications | `list_notifications`, `mark_notification_read`, `mark_notification_unread`, `mark_all_notifications_read`           |
| Your account  | `get_me`, `update_me`, `verify_email`, `resend_verification_code`                                                   |

Each tool calls the same service as its route, after the same checks in the same order: the token, the permission, then the input, validated by the same DTOs. Checks that depend on the record, like `posts.update.own`, are in `PostsService.can()` and `CommentsService.can()`, which the `PostAccess` and `CommentAccess` guards use too, so a rule changed there applies to both. Tools that cannot be undone, deleting and publishing, are marked as destructive, so clients ask before running them. Errors come back as tool errors with the same message as the REST response.

Registering, users, roles and the live notifications stream are REST only. Clients sign in through OAuth rather than a tool, as they need the token before they can call one.

There are also two prompts, which clients offer in a menu: `draft_post` writes a post on a topic and saves it as a draft, completing category names as you type, and `summarize_comments` summarizes a post's comments.

It uses the Streamable HTTP transport statelessly: each request is answered on its own, with plain JSON, so `GET` and `DELETE` respond with `405 Method Not Allowed`. Clients sign in with OAuth, below, so adding it needs only the URL. In Claude Code:

```bash
claude mcp add --transport http nest-demo https://antoha805-nest-demo.duckdns.org/api/mcp
```

Then run `/mcp` and choose to authenticate. In claude.ai, add it as a custom connector with the same URL.

### Signing in with OAuth

The app is an OAuth 2.1 authorization server for MCP clients, as the [MCP authorization spec](https://modelcontextprotocol.io/specification/latest/basic/authorization) describes, built on the SDK's `mcpAuthRouter` with a provider in `src/auth/oauth`. A client finds it on its own:

1. `/api/mcp` without a valid token gets `401 Unauthorized` with `WWW-Authenticate: Bearer resource_metadata="…/.well-known/oauth-protected-resource/api/mcp"`, which names the authorization server.
2. The client reads `/.well-known/oauth-authorization-server` and registers itself at `POST /register` (dynamic client registration, RFC 7591).
3. It opens `/authorize` in the browser with a PKCE challenge. The consent page there asks for the user's email and password, shows the client's name and where it will send them back, and lets them untick writing. It posts to `POST /api/oauth/consent`, which allows 10 requests per minute per IP, like login.
4. The client swaps the code it gets back for tokens at `POST /token`, with the PKCE verifier.

These endpoints are at the root, not under `/api`, where OAuth places them. Every request is limited per IP by the SDK.

- **Access tokens** are JWTs for `/api/mcp` only: their audience is its URL, and login tokens have another, so neither works in the other's place. They last an hour.
- **Refresh tokens** last 30 days from their last use, so a client in use stays signed in. Each refresh replaces the refresh token. If a replaced one is used again, it was copied, so access ends for both copies.
- **Scopes:** `mcp:read` is always granted. `mcp:write` is granted if the client asks for it, or asks for no scope, and the user leaves writing ticked. Without it, the tools that write answer with an error saying so. Either way, each tool still needs the user's permissions.
- **Revoking:** `POST /revoke` with either token, or deleting the user, ends the grant, and its access tokens stop working at once, as each request checks that the grant still exists.
- **Storage:** codes and refresh tokens are stored as SHA-256 hashes, in `oauth_authorization_codes` and `oauth_grants`. Registered clients are in `oauth_clients`, with the secret of confidential clients as is, as the SDK compares it.

The URLs come from `APP_URL`, which must be the public HTTPS URL in production: the SDK refuses an `http` issuer other than localhost.

## Notifications

Modeled on Laravel's notifications. Each kind is a subclass of `Notification` (`src/notifications/notification.ts`) with a `type`, `toDatabase()` for the data it stores, and optionally `via()` to pick its channels and `toBroadcast()` for different live data. `NotificationsService.send(users, notification)` delivers it through each channel, to users given by id or as `NotifiableUser`s, skipping those that do not exist:

- `database` stores it in the `notifications` table, for the list and unread count.
- `broadcast` sends it to the user's open streams.
- `mail` mails it to the user's email. Not in `via()` by default, as the notification needs a `toMail()`.
- `sms` texts it to the user's phone, if they have one. Not in `via()` by default, as the notification needs a `toSms()`.

Like Laravel's `$notifiable`, every method gets whom the notification is for: a `Notifiable` (`src/notifications/notifiable.ts`), which has a `notifiableType` and an `id` and gives the address for mail and SMS through `routeNotificationFor()`. Users are wrapped in a `NotifiableUser` (`src/users/notifiable-user.ts`) with their `nickname`, `email` and `phone`, so the `User` entity stays a database model. A notification for other notifiables names their class as its second type parameter.

The `notifications` table is polymorphic, like Laravel's `morphs('notifiable')`: `notifiableType` and `notifiableId` point to the record it is for, so `notifiableId` cannot have a foreign key. Instead, as for likes, a trigger on `users` deletes the notifications along with the user. Another kind of notifiable needs a value in `NotifiableType`, a migration adding it to the enum, and such a trigger on its table, declared with `@Trigger` on its entity.

The channels run in that order and all use the same id, so a broadcast always names a stored notification, and mail and SMS, the slowest, hold up neither. Sending happens in the request, with no queue, after the change it is about has been saved. A failing channel is logged, stops the channels after it, and does not fail the request.

Sent so far, each to the author when someone else acts, and never for the user's own actions:

- `post.commented`: someone commented on their post. Also mailed, with the comment cut to 200 characters and a link to the post, `APP_URL/api/posts/:id`.
- `post.liked`: someone liked their post.
- `comment.liked`: someone liked their comment.

A like only notifies when it is new, so liking again does not. Unliking and liking again does, as it is a new like.

`GET /api/notifications` pages with cursors, like comments. Marking read and unread responds with `204 No Content`; marking an already read notification keeps when it was first read. Another user's notification returns `404 Not Found`.

`GET /api/notifications/stream` is a [Server-Sent Events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) stream. Each notification arrives as a `notification` event, whose `id` is the notification's and whose data has the same shape as in the list. A comment line is sent every 25 seconds so proxies keep the connection open. The stream needs the token in the `Authorization` header, which the browser's `EventSource` cannot send, so use a client such as [`@microsoft/fetch-event-source`](https://github.com/Azure/fetch-event-source):

```ts
await fetchEventSource('/api/notifications/stream', {
  headers: { Authorization: `Bearer ${token}` },
  onmessage(event) {
    if (event.event === 'notification') {
      const notification = JSON.parse(event.data);
    }
  },
});
```

It sends `Last-Event-ID` when it reconnects, and the stream first replays the notifications missed since that one, oldest first, at most the newest 100. The token is checked when the stream opens, so restart it with a new token when the old one expires.

For a notification badge, `GET /api/auth/me` returns `unreadNotificationsCount`. Each time the stream opens, after the replay, it also sends an `unread-count` event, as `{ "count": 3 }`: set the badge to it, add one for each `notification` event after it, and subtract one for each notification marked as read. So the badge is right again after every reconnection, including for notifications read on another device. Its `id` is the newest notification's, which the count includes, so a reconnection resumes after it.

The streams are kept in memory, which works while a single instance of the app runs. Running more would need them shared, such as through Redis pub/sub.

### Queued notifications

Notifications for many users are sent by a [BullMQ](https://docs.bullmq.io/) queue on Redis rather than in the request. The `api` process runs its worker. When a post is first published, every user but its author gets a `post.published` notification, through `database` and `broadcast`:

1. `PostsService` sets the post's `publishedAt` with an update that only matches drafts, so of concurrent requests only one publishes it and announces it. It then queues a fan-out job, `NotificationQueue.sendToAllUsers()`, with the newest user's id, so users who join later are left out. The job id, `post-published-<postId>`, keeps it to one job.
2. The fan-out job pages through the users by id, 500 at a time, and queues a send job for each page. It pages with a cursor rather than an offset, so users deleted meanwhile do not shift the pages: the cursor is a value, which needs no row of its own. It keeps the cursor with its job, so a retry carries on after the last page it queued, and a send job's id names its first user, so one queued twice is ignored.
3. Each send job makes the notification again and passes its users to `NotificationsService.send`, which loads them in one query, skips those deleted since, and stores their notifications in one statement. A post deleted meanwhile is not announced any more.

A queued job holds a notification as its type and data, such as `{ postId }`, like Laravel stores the models of a queued notification by id. The module that owns a queueable notification registers a factory for its type with `QueuedNotifications`, which makes it again when the job runs, so it shows the records as they are then. See `PostPublishedNotificationFactory`.

Jobs are tried 3 times, waiting longer each time. Finished jobs are kept for a day and failed ones for a week. Redis saves its data to disk and never evicts keys, so queued jobs survive a restart. If Redis is down when a post is published, the post is saved and the failure logged, but nobody is told about the post.

### Mail

A notification sends mail by listing `mail` in `via()` and returning a `MailMessage` from `toMail()`, like Laravel's:

```ts
via() {
  return ['database', 'broadcast', 'mail'];
}

toMail(user: NotifiableUser) {
  return new MailMessage()
    .subject('New comment on your post')
    .greeting(`Hi ${user.nickname}!`)
    .line(`${this.commenter.nickname} commented on "${this.post.title}".`)
    .action('View the post', `/posts/${this.post.id}`)
    .salutation('Regards, nest-demo');
}
```

It renders as plain text and HTML, with the lines and buttons in the order they were added, and the content escaped in the HTML. Relative button links are added to `APP_URL`, keeping its path, so `/posts/1` with `APP_URL=https://example.com/api` links to `https://example.com/api/posts/1`. Only `http` and `https` links are allowed. Each user gets their own mail, so one that fails is logged and does not stop the others. Users deleted in the meantime are skipped.

`MAIL_MAILER` picks how mails are sent, like Laravel's:

- `smtp` sends them through the SMTP server of `MAIL_URL`, from `MAIL_FROM`.
- `ses` sends them through [Amazon SES](https://aws.amazon.com/ses/) in `AWS_REGION`, from `MAIL_FROM`. The AWS SDK is loaded only for this mailer.
- `log` writes them to the log instead, including the address and text, as in development. It is the default, also when `MAIL_MAILER` is empty, so the mail channel is never left out.

As mails are sent within the request, a slow mail server slows down the request that sent the notification; a queue would fix that once it matters.

#### Amazon SES

- **Credentials** are found by the AWS SDK as usual: `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, or, on EC2, the instance's IAM role, which needs `ses:SendEmail` and keeps keys out of `prod.env`.
- **The instance role from inside Docker** needs the instance metadata hop limit raised to 2, as the container is one hop further than IMDSv2 allows by default: `aws ec2 modify-instance-metadata-options --instance-id <id> --http-put-response-hop-limit 2 --http-endpoint enabled`. Without it, sending fails with a credentials error.
- **The sender** in `MAIL_FROM` has to be an identity verified in SES: its address, or better its domain.
- **New SES accounts are in the sandbox**: they only mail verified addresses, and a limited number per day, until production access is requested in the SES console.

### SMS

A notification sends texts by listing `sms` in `via()` and returning an `SmsMessage` from `toSms()`, like Laravel's `VonageMessage`:

```ts
via() {
  return ['database', 'broadcast', 'sms'];
}

toSms(user: NotifiableUser) {
  return new SmsMessage().content(
    `${this.commenter.nickname} commented on "${this.post.title}".`,
  );
}
```

Texts go to the user's `phone`, which they set with `PATCH /api/auth/me` as `{ "phone": "+4915112345678" }` and remove with `{ "phone": null }`. It is stored in [E.164](https://en.wikipedia.org/wiki/E.164), with spaces, dashes, dots and parentheses dropped, and shown only to the user in `GET /api/auth/me`. It is not confirmed yet, so a user could enter someone else's number. Users without a phone are skipped, so a notification can list `sms` for everyone. As with mail, each user gets their own text, and one that fails does not stop the others.

`SMS_DRIVER` picks how texts are sent:

- `sns` sends them through [Amazon SNS](https://docs.aws.amazon.com/sns/latest/dg/sns-mobile-phone-number-as-subscriber.html) in `AWS_REGION`, as transactional texts, with `SMS_FROM` as the sender ID if set and the country allows one. Credentials are found as for SES, and the IAM role needs `sns:Publish`. New accounts are in the SMS sandbox, which only texts verified numbers until production access is requested. The AWS SDK is loaded only for this driver.
- `twilio` sends them through [Twilio's Messages API](https://www.twilio.com/docs/messaging/api/message-resource) with `TWILIO_ACCOUNT_SID` and `TWILIO_AUTH_TOKEN`, from `SMS_FROM`: a Twilio number, an alphanumeric sender ID, or a messaging service SID (`MG...`). It uses the [twilio](https://www.npmjs.com/package/twilio) SDK, loaded only for this driver, and gives up after 10 seconds. A refused text fails with its Twilio error code, such as 21211 for an invalid number.
- `log` writes them to the log instead, including the number and text, as in development. It is the default, also when `SMS_DRIVER` is empty, so the sms channel is never left out.

Another provider takes a class implementing `SmsTransport` (`src/sms/sms-transport.ts`), a name in `SMS_DRIVERS` and its settings in `src/config/env.validation.ts`, and a case in `SmsSender.createTransport`.

## Pagination

`GET /api/posts` accepts `page` (default `1`) and `limit` (default `20`, at most `100`), and lists posts newest first:

```json
{ "data": [], "total": 42, "page": 1, "limit": 20, "totalPages": 3 }
```

A page past the end has an empty `data`.

`GET /api/posts/:postId/comments` uses cursors instead, as comments are added and deleted while people read them. It accepts `cursor` and `limit` (default `20`, at most `100`), and lists comments newest first:

```json
{ "data": [], "limit": 20, "nextCursor": "019a…" }
```

To get the next page, send `nextCursor` as `cursor`. It is `null` on the last page. The total is the post's `commentsCount`.

`GET /api/posts/:id` also returns the first page of comments in the same format under `comments`. The other post routes do not.

## Seeding

`npm run seed` adds sample categories, posts, comments and likes. It can be run repeatedly: existing categories are updated, everything else that exists is left unchanged, and nothing is deleted.

The comments and likes come from three users, such as `seed-ana@example.com`, with random passwords that are not kept, so nobody can log in as them. Register your own user to see `myLikeAt` and `myLastCommentAt` change.

## Tests

`npm run test:e2e` runs the API tests against a separate `nest_demo_test` database on the Postgres server from `.env`, which must be running. Each run drops and recreates that database and applies all migrations, so your development data is not touched.
