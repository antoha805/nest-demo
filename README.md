# nest-demo

Demo REST API built with NestJS, MikroORM and PostgreSQL.

Requires Node.js 22.17+ and Docker.

## Getting started

```bash
cp .env.example .env
docker compose up --watch
```

In a second terminal, add the sample data:

```bash
docker compose exec api npm run seed
```

The API is served at `http://localhost:3000/api` and reloads when files in `src` change. Postgres is exposed on host port `5433`.

To run the API on the host instead, start only the database:

```bash
npm install
docker compose up -d --wait postgres
npm run migration:run
npm run permissions:sync
npm run seed
npm run start:dev
```

## Migrations

The schema is managed by MikroORM migrations in `src/database/migrations`, run by `src/database/migrate.ts`. The app never changes the schema itself. `docker compose up` applies pending migrations when the `api` container starts.

Primary keys are UUID v7 values generated by the database's `uuidv7()` function, which requires Postgres 18 or newer.

After changing an entity, generate a migration from the host, with Postgres running and all existing migrations applied:

```bash
npm run migration:create -- AddPostSlug
```

This writes the difference between the entities and the database to a new file in `src/database/migrations`. Review it, then add its class to the end of the list in `src/database/migrations/index.ts`: migrations are listed there rather than found on disk, so they load the same way from `src` and `dist`.

Then apply it with `docker compose exec api npm run migration:run`, or `npm run migration:run` on the host. `npm run migration:revert` undoes the latest one, and `npm run migration:check` fails if the entities and the database differ.

The project moved from TypeORM, whose migrations kept their names. On a database TypeORM migrated, the first `migration:run` records them as applied from its `migrations` table instead of running them again. A later migration then drops that table. To deploy the TypeORM version again, first run `npm run migration:revert` once, which restores the table.

## Production image

```bash
docker build --target prod -t nest-demo .
```

The image contains no `.env`, so pass the settings below as environment variables when running it.

The app does not apply migrations on startup. Run them once as a deploy step before starting the new version:

```bash
docker run --rm --env-file prod.env nest-demo npm run migration:run:prod
docker run --rm --env-file prod.env nest-demo npm run permissions:sync:prod
```

## Production deployment

`docker-compose.prod.yml` runs the production image with Postgres, and applies pending migrations and syncs permissions before the API starts. Create `prod.env` from `.env.example` with a strong `DB_PASSWORD`; it is not committed. The file sets `DB_HOST`, `DB_PORT` and `LOG_TRANSPORTS` itself.

Build and push the image from another machine, as small instances can run out of memory while building. Match the instance's CPU architecture, for example `--platform linux/amd64` for `t3`:

```bash
API_IMAGE=registry.example.com/nest-demo docker compose -f docker-compose.prod.yml --env-file prod.env build
docker push registry.example.com/nest-demo
```

Then, on the instance, with `docker-compose.prod.yml` and `prod.env` in the same directory:

```bash
export API_IMAGE=registry.example.com/nest-demo
docker compose -f docker-compose.prod.yml --env-file prod.env pull api migrate
docker compose -f docker-compose.prod.yml --env-file prod.env up -d --no-build
```

Only Caddy is published to the host. It serves the API over HTTPS on port `443` and redirects port `80` to it, using a free Let's Encrypt certificate that it renews itself. Set `DOMAIN` in `prod.env` to a name that points to the instance, and allow both ports in the security group. `PORT` only sets the port inside the container.

### Automatic deployment

Each push to `main` runs the checks in `.github/workflows/deploy.yml`, then publishes an Arm image to `ghcr.io/antoha805/nest-demo`. A systemd timer on the instance checks for a new image and compose file every minute, and applies them with pending migrations.

To set up an instance, copy the `deploy` directory to it, add `API_IMAGE=ghcr.io/antoha805/nest-demo` to `prod.env`, then run:

```bash
sudo install -m 755 deploy/auto-deploy.sh /usr/local/bin/nest-demo-auto-deploy
sudo cp deploy/nest-demo-deploy.service deploy/nest-demo-deploy.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now nest-demo-deploy.timer
```

A failed deploy does not show up in GitHub. To see what the instance did, run `journalctl -u nest-demo-deploy -n 50`.

## Configuration

Settings are read from environment variables and `.env`; see `.env.example`. Real environment variables take precedence over `.env`.

| Variable         | Required    | Description                                                                        |
| ---------------- | ----------- | ---------------------------------------------------------------------------------- |
| `PORT`           | No          | API port (default `3000`)                                                          |
| `LOG_LEVEL`      | No          | `fatal`, `error`, `warn`, `info`, `debug`, `trace` or `silent` (default `info`)    |
| `LOG_TRANSPORTS` | No          | Comma-separated log destinations, see below (default `stdout`)                     |
| `DB_HOST`        | Yes         | Postgres host                                                                      |
| `DB_PORT`        | Yes         | Postgres port                                                                      |
| `DB_USERNAME`    | Yes         | Postgres user                                                                      |
| `DB_PASSWORD`    | Yes         | Postgres password                                                                  |
| `DB_NAME`        | Yes         | Postgres database                                                                  |
| `JWT_SECRET`     | Yes         | Key that signs access tokens, at least 32 characters                               |
| `JWT_EXPIRES_IN` | No          | Access token lifetime in seconds (default `3600`)                                  |
| `APP_URL`        | No          | Where links in mails point, such as the frontend (default `http://localhost:3000`) |
| `MAIL_MAILER`    | No          | How mails are sent: `smtp` or `log`. Unset or empty turns mail off                 |
| `MAIL_URL`       | With `smtp` | SMTP server, such as `smtps://user:password@smtp.example.com:465`                  |
| `MAIL_FROM`      | With `smtp` | Sender of mails, such as `nest-demo <noreply@example.com>`                         |

They are validated at startup, and the app exits with an error listing any missing or invalid values.

## Logging

`LOG_TRANSPORTS` selects where logs go. Every log line is sent to all listed transports, for example `LOG_TRANSPORTS=stdout,file`.

| Transport | Destination                                                                      |
| --------- | -------------------------------------------------------------------------------- |
| `stdout`  | JSON on stdout                                                                   |
| `pretty`  | Readable output on stdout, for development (not available in the prod image)     |
| `file`    | JSON in `logs/app.log`, which is not rotated (mount a volume to keep it in prod) |

To add a transport, add its pino transport target to `src/config/log-transports.ts`.

## Authentication and authorization

`POST /api/auth/register` and `POST /api/auth/login` return an `accessToken`. Send it as `Authorization: Bearer <token>`. Both endpoints allow 10 requests per minute per IP.

A user holds roles, each role grants permissions, and permissions can also be granted to a user directly. They are read from the database on every request, so changes apply immediately to tokens already issued. Passwords are hashed with bcrypt.

New users get the `member` role. The API cannot grant the first admin, so register a user and promote them from the command line:

```bash
npm run make-admin -- alice@example.com
```

In production, use `docker compose -f docker-compose.prod.yml --env-file prod.env exec api npm run make-admin:prod -- alice@example.com`.

`npm run permissions:sync` makes the database match the permissions in the code, as the API can only assign them, not create them. It runs after migrations on every `docker compose up` and deploy, and is safe to re-run. `admin` always gets every permission and cannot be changed or deleted. `editor` and `member` are created with the permissions in `src/roles/permission-names.ts` if they are missing, so a deleted `editor` role comes back. After that they only get permissions that are new, so edits made through the API are kept. `member` cannot be renamed or deleted, as registration assigns it.

Every route requires a token unless marked `@Public()`. Permissions are checked with [CASL](https://casl.js.org): `src/casl/casl-ability.factory.ts` turns each permission a user holds into rules. To protect a route, add `@CheckPolicies((ability) => ability.can('create', Post))`, which responds with `403 Forbidden` if the check fails. Rules that depend on the record, like `posts.update.own`, need a guard that loads it, as `@PostAccess('update')` does in `src/posts/post-access.guard.ts`.

To add a permission, add it to `src/roles/permission-names.ts` and its rules to `PERMISSION_RULES` in the ability factory, which fails to compile until you do. The next sync inserts it and grants it to `admin` and to the roles that have it in their defaults.

Removing a name from that file makes the next sync delete the permission and all its grants, including those on custom roles and users, and deploying an older version does the same. Renaming counts as removing one and adding another, so custom roles and users lose it. To keep their grants, rename the permission in a migration, which runs before the sync.

A category that still has posts cannot be deleted (`409 Conflict`). Categories return `postsCount`, which only counts published posts, so it is the same for every user and does not reveal drafts.

A post's `authorId` is set to the logged-in user when it is created and cannot be changed through the API. It is `null` for older posts and sample data, and becomes `null` if the author is deleted.

The `.all` permissions apply to every post, and the `.own` ones only to posts the user wrote. Posts with no author need `.all`.

Posts are drafts until published, which requires `posts.publish`. Without it, a user can only create drafts, and editing a published post turns it back into a draft. Published posts are public. Drafts are visible only to their author and to users with `posts.publish`, and return `404 Not Found` to anyone else, so send the token on `GET` requests to see them.

Comments and likes follow the post: every route above returns `404 Not Found` if the user cannot read the post, including for a comment they wrote on a post that has since become a draft. Comments stay when their author is deleted, with `authorId` set to `null`, and are deleted with their post. Posts return their total as `commentsCount`, and `myLastCommentAt` holds when the logged-in user last commented on them, or `null` if they have not or no token was sent. Comments can only be edited by their author; `comments.delete.all` is for moderation.

Liking and unliking are idempotent and respond with `204 No Content`. Posts and comments return their total as `likesCount`, and `myLikeAt` holds when the logged-in user liked them, or `null` if they have not or no token was sent. The `likes` table is polymorphic: `likeableType` and `likeableId` point to a post or comment. As Postgres cannot enforce a foreign key on that, database triggers delete the likes along with their post or comment. Adding a new likeable type needs a new enum value and such a trigger.

## Notifications

Modeled on Laravel's notifications. Each kind is a subclass of `Notification` (`src/notifications/notification.ts`) with a `type`, `toDatabase()` for the data it stores, and optionally `via()` to pick its channels and `toBroadcast()` for different live data. `NotificationsService.send(userIds, notification)` delivers it through each channel:

- `database` stores it in the `notifications` table, for the list and unread count.
- `broadcast` sends it to the user's open streams.
- `mail` mails it to the user's email. Not in `via()` by default, as the notification needs a `toMail()`. Left out while mail is off, so notifications that list it are still sent through the others.

The channels run in that order and all use the same id, so a broadcast always names a stored notification, and mail, the slowest, holds up neither. Sending happens in the request, with no queue, after the change it is about has been saved. A failing channel is logged, stops the channels after it, and does not fail the request.

Sent so far, each to the author when someone else acts, and never for the user's own actions:

- `post.commented`: someone commented on their post.
- `post.liked`: someone liked their post.
- `comment.liked`: someone liked their comment.

A like only notifies when it is new, so liking again does not. Unliking and liking again does, as it is a new like.

`GET /api/notifications` pages with cursors, like comments. Marking read and unread responds with `204 No Content`; marking an already read notification keeps when it was first read. Another user's notification returns `404 Not Found`.

`GET /api/notifications/stream` is a [Server-Sent Events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) stream. Each notification arrives as a `notification` event, whose `id` is the notification's and whose data has the same shape as in the list. A comment line is sent every 25 seconds so proxies keep the connection open. The stream needs the token in the `Authorization` header, which the browser's `EventSource` cannot send, so use a client such as [`@microsoft/fetch-event-source`](https://github.com/Azure/fetch-event-source):

```ts
await fetchEventSource('/api/notifications/stream', {
  headers: { Authorization: `Bearer ${token}` },
  onmessage(event) {
    if (event.event === 'notification') {
      const notification = JSON.parse(event.data);
    }
  },
});
```

It sends `Last-Event-ID` when it reconnects, and the stream first replays the notifications missed since that one, oldest first, at most the newest 100. The token is checked when the stream opens, so restart it with a new token when the old one expires.

The streams are kept in memory, which works while a single instance of the app runs. Running more would need them shared, such as through Postgres `LISTEN/NOTIFY`.

### Mail

A notification sends mail by listing `mail` in `via()` and returning a `MailMessage` from `toMail()`, like Laravel's:

```ts
via() {
  return ['database', 'broadcast', 'mail'];
}

toMail(user: MailRecipient) {
  return new MailMessage()
    .subject('New comment on your post')
    .greeting(`Hi ${user.nickname}!`)
    .line(`${this.commenter.nickname} commented on "${this.post.title}".`)
    .action('View the post', `/posts/${this.post.id}`)
    .salutation('Regards, nest-demo');
}
```

It renders as plain text and HTML, with the lines and buttons in the order they were added, and the content escaped in the HTML. Button links are resolved against `APP_URL`, and only `http` and `https` links are allowed. Each user gets their own mail, so one that fails is logged and does not stop the others. Users deleted in the meantime are skipped.

`MAIL_MAILER` picks how mails are sent, like Laravel's:

- `smtp` sends them through the SMTP server of `MAIL_URL`, from `MAIL_FROM`.
- `log` writes them to the log instead, including the address and text, as in development.
- Unset or empty turns mail off: the mail channel is left out, and the app logs so at startup.

As mails are sent within the request, a slow SMTP server slows down the request that sent the notification; a queue would fix that once it matters.

## Pagination

`GET /api/posts` accepts `page` (default `1`) and `limit` (default `20`, at most `100`), and lists posts newest first:

```json
{ "data": [], "total": 42, "page": 1, "limit": 20, "totalPages": 3 }
```

A page past the end has an empty `data`.

`GET /api/posts/:postId/comments` uses cursors instead, as comments are added and deleted while people read them. It accepts `after` and `limit` (default `20`, at most `100`), and lists comments newest first:

```json
{ "data": [], "limit": 20, "nextCursor": "019a…" }
```

To get the next page, send `nextCursor` as `after`. It is `null` on the last page. The total is the post's `commentsCount`.

`GET /api/posts/:id` also returns the first page of comments in the same format under `comments`. The other post routes do not.

## Seeding

`npm run seed` adds sample categories, posts, comments and likes. It can be run repeatedly: existing categories are updated, everything else that exists is left unchanged, and nothing is deleted.

The comments and likes come from three users, such as `seed-ana@example.com`, with random passwords that are not kept, so nobody can log in as them. Register your own user to see `myLikeAt` and `myLastCommentAt` change.

## Tests

`npm run test:e2e` runs the API tests against a separate `nest_demo_test` database on the Postgres server from `.env`, which must be running. Each run drops and recreates that database and applies all migrations, so your development data is not touched.
