# nest-demo

Demo REST API built with NestJS, TypeORM and PostgreSQL.

Requires Node.js 20.19+ and Docker.

## Getting started

```bash
cp .env.example .env
docker compose up --watch
```

In a second terminal, add the sample data:

```bash
docker compose exec api npm run seed
```

The API is served at `http://localhost:3000/api` and reloads when files in `src` change. Postgres is exposed on host port `5433`.

To run the API on the host instead, start only the database:

```bash
npm install
docker compose up -d --wait postgres
npm run migration:run
npm run permissions:sync
npm run seed
npm run start:dev
```

## Migrations

The schema is managed by TypeORM migrations in `src/database/migrations`. `synchronize` is off in every environment. `docker compose up` applies pending migrations when the `api` container starts.

Primary keys are UUID v7 values generated by the database's `uuidv7()` function, which requires Postgres 18 or newer.

After changing an entity, generate a migration from the host, with Postgres running and all existing migrations applied:

```bash
npm run migration:generate -- src/database/migrations/AddPostSlug
```

Then apply it with `docker compose exec api npm run migration:run`, or `npm run migration:run` on the host. `npm run migration:revert` undoes the latest one.

## Production image

```bash
docker build --target prod -t nest-demo .
```

The image contains no `.env`, so pass the settings below as environment variables when running it.

The app does not apply migrations on startup. Run them once as a deploy step before starting the new version:

```bash
docker run --rm --env-file prod.env nest-demo npm run migration:run:prod
docker run --rm --env-file prod.env nest-demo npm run permissions:sync:prod
```

## Production deployment

`docker-compose.prod.yml` runs the production image with Postgres, and applies pending migrations and syncs permissions before the API starts. Create `prod.env` from `.env.example` with a strong `DB_PASSWORD`; it is not committed. The file sets `DB_HOST`, `DB_PORT` and `LOG_TRANSPORTS` itself.

Build and push the image from another machine, as small instances can run out of memory while building. Match the instance's CPU architecture, for example `--platform linux/amd64` for `t3`:

```bash
API_IMAGE=registry.example.com/nest-demo docker compose -f docker-compose.prod.yml --env-file prod.env build
docker push registry.example.com/nest-demo
```

Then, on the instance, with `docker-compose.prod.yml` and `prod.env` in the same directory:

```bash
export API_IMAGE=registry.example.com/nest-demo
docker compose -f docker-compose.prod.yml --env-file prod.env pull api migrate
docker compose -f docker-compose.prod.yml --env-file prod.env up -d --no-build
```

Only Caddy is published to the host. It serves the API over HTTPS on port `443` and redirects port `80` to it, using a free Let's Encrypt certificate that it renews itself. Set `DOMAIN` in `prod.env` to a name that points to the instance, and allow both ports in the security group. `PORT` only sets the port inside the container.

### Automatic deployment

Each push to `main` runs the checks in `.github/workflows/deploy.yml`, then publishes an Arm image to `ghcr.io/antoha805/nest-demo`. A systemd timer on the instance checks for a new image and compose file every minute, and applies them with pending migrations.

To set up an instance, copy the `deploy` directory to it, add `API_IMAGE=ghcr.io/antoha805/nest-demo` to `prod.env`, then run:

```bash
sudo install -m 755 deploy/auto-deploy.sh /usr/local/bin/nest-demo-auto-deploy
sudo cp deploy/nest-demo-deploy.service deploy/nest-demo-deploy.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now nest-demo-deploy.timer
```

A failed deploy does not show up in GitHub. To see what the instance did, run `journalctl -u nest-demo-deploy -n 50`.

## Configuration

Settings are read from environment variables and `.env`; see `.env.example`. Real environment variables take precedence over `.env`.

| Variable         | Required | Description                                                                     |
| ---------------- | -------- | ------------------------------------------------------------------------------- |
| `PORT`           | No       | API port (default `3000`)                                                       |
| `LOG_LEVEL`      | No       | `fatal`, `error`, `warn`, `info`, `debug`, `trace` or `silent` (default `info`) |
| `LOG_TRANSPORTS` | No       | Comma-separated log destinations, see below (default `stdout`)                  |
| `DB_HOST`        | Yes      | Postgres host                                                                   |
| `DB_PORT`        | Yes      | Postgres port                                                                   |
| `DB_USERNAME`    | Yes      | Postgres user                                                                   |
| `DB_PASSWORD`    | Yes      | Postgres password                                                               |
| `DB_NAME`        | Yes      | Postgres database                                                               |
| `JWT_SECRET`     | Yes      | Key that signs access tokens, at least 32 characters                            |
| `JWT_EXPIRES_IN` | No       | Access token lifetime in seconds (default `3600`)                               |

They are validated at startup, and the app exits with an error listing any missing or invalid values.

## Logging

`LOG_TRANSPORTS` selects where logs go. Every log line is sent to all listed transports, for example `LOG_TRANSPORTS=stdout,file`.

| Transport | Destination                                                                      |
| --------- | -------------------------------------------------------------------------------- |
| `stdout`  | JSON on stdout                                                                   |
| `pretty`  | Readable output on stdout, for development (not available in the prod image)     |
| `file`    | JSON in `logs/app.log`, which is not rotated (mount a volume to keep it in prod) |

To add a transport, add its pino transport target to `src/config/log-transports.ts`.

## Authentication and authorization

`POST /api/auth/register` and `POST /api/auth/login` return an `accessToken`. Send it as `Authorization: Bearer <token>`. Both endpoints allow 10 requests per minute per IP.

A user holds roles, each role grants permissions, and permissions can also be granted to a user directly. They are read from the database on every request, so changes apply immediately to tokens already issued. Passwords are hashed with bcrypt.

New users get the `member` role. The API cannot grant the first admin, so register a user and promote them from the command line:

```bash
npm run make-admin -- alice@example.com
```

In production, use `docker compose -f docker-compose.prod.yml --env-file prod.env exec api npm run make-admin:prod -- alice@example.com`.

`npm run permissions:sync` stores the permissions from the code and three roles in the database. It runs after migrations on every `docker compose up` and deploy, and is safe to re-run. `admin` always gets every permission and cannot be changed or deleted. `editor` and `member` start with the permissions in `src/roles/permission-names.ts`, and are only created if missing, so edits made through the API are kept but a deleted `editor` role comes back. `member` cannot be renamed or deleted, as registration assigns it.

Every route requires a token unless marked `@Public()`. Permissions are checked with [CASL](https://casl.js.org): `src/casl/casl-ability.factory.ts` turns each permission a user holds into rules. To protect a route, add `@CheckPolicies((ability) => ability.can('create', Post))`, which responds with `403 Forbidden` if the check fails. Rules that depend on the record, like `posts.update.own`, need a guard that loads it, as `@PostAccess('update')` does in `src/posts/post-access.guard.ts`.

To add a permission, add it to `src/roles/permission-names.ts` and its rules to `PERMISSION_RULES` in the ability factory, which fails to compile until you do. The next sync inserts it and grants it to `admin`. Removing a name from that file does not delete the permission from the database, so write a migration for that.

## Endpoints

| Method | Path                         | Permission                               | Description                    |
| ------ | ---------------------------- | ---------------------------------------- | ------------------------------ |
| POST   | `/api/auth/register`         | Public                                   | Create an account              |
| POST   | `/api/auth/login`            | Public                                   | Get an access token            |
| GET    | `/api/auth/me`               | Any logged-in user                       | Get your roles and permissions |
| POST   | `/api/categories`            | `categories.create`                      | Create a category              |
| GET    | `/api/categories`            | Public                                   | List categories                |
| GET    | `/api/categories/:id`        | Public                                   | Get a category                 |
| PATCH  | `/api/categories/:id`        | `categories.update`                      | Update a category              |
| DELETE | `/api/categories/:id`        | `categories.delete`                      | Delete a category              |
| POST   | `/api/posts`                 | `posts.create`                           | Create a post                  |
| GET    | `/api/posts`                 | Public                                   | List posts                     |
| GET    | `/api/posts/:id`             | Public                                   | Get a post                     |
| PATCH  | `/api/posts/:id`             | `posts.update.all` or `posts.update.own` | Update a post                  |
| DELETE | `/api/posts/:id`             | `posts.delete.all` or `posts.delete.own` | Delete a post                  |
| GET    | `/api/users`                 | `users.read`                             | List users                     |
| GET    | `/api/users/:id`             | `users.read`                             | Get a user                     |
| PUT    | `/api/users/:id/roles`       | `users.manage`                           | Replace a user's roles         |
| PUT    | `/api/users/:id/permissions` | `users.manage`                           | Replace direct permissions     |
| DELETE | `/api/users/:id`             | `users.manage`                           | Delete a user                  |
| POST   | `/api/roles`                 | `roles.manage`                           | Create a role                  |
| GET    | `/api/roles`                 | `roles.read`                             | List roles                     |
| GET    | `/api/roles/:id`             | `roles.read`                             | Get a role                     |
| PATCH  | `/api/roles/:id`             | `roles.manage`                           | Update a role                  |
| DELETE | `/api/roles/:id`             | `roles.manage`                           | Delete a role                  |
| GET    | `/api/permissions`           | `roles.read`                             | List permissions               |

A category that still has posts cannot be deleted (`409 Conflict`).

A post's `authorId` is set to the logged-in user when it is created and cannot be changed through the API. It is `null` for older posts and sample data, and becomes `null` if the author is deleted.

The `.all` permissions apply to every post, and the `.own` ones only to posts the user wrote. Posts with no author need `.all`.

Posts are drafts until published, which requires `posts.publish`. Without it, a user can only create drafts, and editing a published post turns it back into a draft. Published posts are public. Drafts are visible only to their author and to users with `posts.publish`, and return `404 Not Found` to anyone else, so send the token on `GET` requests to see them.

## Seeding

`npm run seed` adds sample categories and posts. It can be run repeatedly: existing categories are updated, existing posts are left unchanged, and nothing is deleted.

## Tests

`npm run test:e2e` runs the API tests against a separate `nest_demo_test` database on the Postgres server from `.env`, which must be running. Each run drops and recreates that database and applies all migrations, so your development data is not touched.
